# 2026-10-19

## relayFile 传输逻辑评审

通读 `Core/Protocol`、`Core/Net`、`Core/File`、`Gui/Form/RelayTask.cpp`，产出 `TRANSFER-REVIEW.md`（仓库根目录）。

结论要点（P0）：
1. 接收端 `handleRecvChuck` 先回 ACK 再写盘，写失败只 warning → 双方报成功但文件损坏。
2. 接收端直接写最终路径（WriteOnly 截断），失败即毁原文件；应改 `.part` + 校验 + 原子 rename。
3. 完成语义无握手，`Answer_Complete` 等 5 个类型定义未用；发送方发完 Complete 即报成功。
4. 帧无 CRC、无 body 长度上限；假帧头 + 巨大正 len 会让 `UnPack` 永久等待并吃内存。

架构层：`OneFileTrans`/`FileSession` 归属 GUI 线程，每个 256KB 块要两次跨线程排队 + GUI 线程写盘（ACK 延迟的根因）；`RunTaskItem` 忙等无总超时；存在性检查是 O(N) 次串行 RTT。

构建验证：MSYS2 UCRT64 + Qt6（`/c/msys64/ucrt64`），`cmake -S . -B build-review -G Ninja -DRF_USE_GUI=OFF -DRF_USE_MINGW=ON -DRF_BUILD_TESTS=ON` 可编译通过；`relayFileTransTest server|sender|receiver` 可做端到端压测（200MB/1GB 均 41MB/s，SHA-256 一致）。
注意：后台进程必须用 run_in_background，`&` 启动会被回收。

## 第一批改造实施完成

按评审文档"第一批"6 项落地（不改协议格式）：

1. `OneFileTrans` 接收写 `<目标>.relaypart`，`finalizeRecvFile` 做 flush + 字节数校验 + 删旧文件 + `QFile::rename`；`discardPartFile` 在失败/取消/超时时清理。
2. `handleRecvChuck` 改为先写盘（循环处理短写）再 `curBlockIndex_++` 并回 ACK；写失败走 `failAndInterrupt`。
3. 新增完成握手：`sendCompleteFrame` / `answerComplete` / `handleCompleteAnswer`。发送方发完整数据后进入等待 `Answer_Complete`，超时重发 Complete 最多 3 次；接收方 `completeAnswered_` 幂等重放 Answer。
4. `Message` / `FileMeta` 四个特殊成员全 `= default`，删手写实现；`pushTask` 里补 `resp.uuid` 的临时补丁已删。
5. `FileSession::Quit` / `ControlSession::Quit` 幂等，`ClientCore`（含 QTcpSocket）用 `BlockingQueuedConnection` 回 worker 线程内 delete；`onCancelWaitMsg` 先移出容器再锁外回调；`WaiteFrame` 新增 `done` 原子标志防重复 set_value。
6. `ClientCore::onReadyRead`、`FileSession::handleFrame`、`ControlSession::handleFrame` 全部加 try/catch。

顺带：Finished/Interrupted 下收 Cancel 不再回 Cancel（消除互发死循环）；发送方收到意外 `Request_Complete` 不再删本地临时归档。

实测：200MB 与 5MB（覆盖已存在文件）SHA-256/cmp 一致、无 `.relaypart` 残留；传 1GB 中 kill 发送端后原目标文件未被截断、残片 162MB 在 `.relaypart`、接收方 15s 超时自动删除；退出无 QSocketNotifier/QThread 警告。

遗留：强杀进程会留 `.relaypart`（待做启动清理或续传）；第二批（新帧格式 + flags 拆位 + 字节窗口）未动。

## 第二批改造实施完成（协议不兼容旧版）

1. **新帧格式**（`Core/Protocol/Protocol.{h,cpp}` 全量重写）：
   `magic(4) ver(2) flags(2) type(2) rsv(2) sessionId(8) index(8) frameLen(4) headerCrc(4)` + 变长路由字段 + body + 可选 bodyCrc。
   `kFixedHeaderSize=36`、`kMaxFrameSize=32MB`、body ≤64KB 才带 CRC、路由字段 u8 长度（>255 时 Pack 返回空）。
   `UnPack` 改成 `UnPackResult{NeedMoreData,Ok,ProtocolError}`，头部 CRC 不符按假 magic 跳 1 字节重同步，前导垃圾只留末 3 字节。
2. **flags 拆位**：`OneFrame::mark` → `flags`（FromReceiver/Encrypted/BodyCrc）；`Message::mark` → `Message::flags`（kRecursiveList/kArchive）；`Ask_*` 结果码改用 `msgStateCode`。`getMapKeyUUIDByMark` → `getMapKeyUUIDByDirection`。
3. **字节窗口 + 累积 ACK + SACK + 协商**（`OneFileTrans`）：
   窗口 4MB 按字节；块大小接收方决定（64KB/256KB/1MB 按文件大小），经 `Answer_Send`/`Request_Start` 的 `Message.blockSize/windowBytes` 协商；ACK.index = 下一个期望块，`data` = 256 位 SACK 位图；ACK 节流 1MB/20ms；接收端支持乱序 seek 写入；发送端只重传空洞。

新增测试 `Console/UnpackTest.cpp` 重写为 14 项（编解码 + 发送侧 SACK 只重传空洞 + 接收侧乱序落盘）。

实测：200MB 66.7MB/s（第一批 38MB/s，同 Debug 构建）、320MB(1MB 块) 66.2MB/s、2MB(64KB 块) 0.16s，均 cmp 一致；中断测试原文件未破坏；GUI 目标用 `-DQT_DEFAULT_MAJOR_VERSION=6 -DQAPPLICATION_CLASS=QApplication`（MSYS2 Qt6 Widgets）编译通过 0 warning，验证了 API 变更没有漏改调用点。

遗留：合并窗口最大 256 块；块大小/窗口是单向协商、无 RTT 自适应；整文件哈希校验未接（可复用 AskSha256）。


## 第三批（架构）完成
- 新增 `Core/Net/FileSessionIO.{h,cpp}`：传输引擎（transferMap_ + OneFileTrans + 读写盘）跑在独立 IO 线程；`FileSession` 退化为门面（投递 + 转发信号），公开方法可跨线程调用。
- 关键坑1：收帧/发帧必须 DirectConnection 直连 IO 线程对象。走 FileSession 门面会把信号排队到 GUI 线程，GUI 在 RunTaskItem 里一阻塞就互锁（表现为对端永远收不到 Answer_Send）。
- 关键坑2：心跳 QTimer 原来在 GUI 线程，界面卡 15s 就被服务器踢，走控制连接的 Request_Complete 全发不出去；已搬进控制连接套接字线程（DoubleLinker::startHeartbeat）。
- `ClientCore` 的 ClientInfo 加锁，`isConnected()` 改 atomic。
- RunTaskItem 改 std::condition_variable + 两级超时（创建 30s / 总兜底 6h），去掉 msleep(1)+processEvents 忙等。
- 批量查询：BaseAskDF 新增 AskFileMetaBatch / AskFileSamplesBatch（400/200 分片），Message 加 sampleMap；RelayTask::onBaseCheck 批量化 + 单文件缺失只跳过。
- 断点续传：Message 加 resumeOffset / resumeFingerprint；FileDir::QuickFingerprint(path, 期望总长)；tryReusePartFile 只认块对齐前缀 + 指纹一致；超时保留 .relaypart、显式取消才删。
- 实测 200MB 77.9MB/s、1GB 82.2MB/s（第二批 66.7），100MB 残片续传/伪造残片丢弃均正确，UnpackTest 14 项全过，GUI 0 warning。

## 更正：ControlSession 线程归属（原文档结论有误）
复查后确认 `TRANSFER-REVIEW.md` 里"ControlSession 的递归列目录/算 sha256/打 tar 包会卡界面"是错的：
- `ControlSession` 对象在 GUI 线程（relayFile.cpp:26），`handleFrame` 经 QueuedConnection 进 GUI 线程（ClientHelper.cpp:275）；
- 但 `Ask_FileList/Ask_Sha256/Ask_Archive/Ask_FileMeta/Ask_FileSamples` 全走 `dispatchMessage` → `workerPool_(ThreadPool(3))`，`Ask_ArchivePack` 的 tar.xz 打包也入池；
- 请求方列目录在 ExplorerControl / RelayTask 各自的 WorkerThread，配 WaitDialog 嵌套事件循环 + future.get() 阻塞 worker 线程。
真正遗留：① `handleFrame` 的整帧 deserializeStruct 在 GUI 线程（大 Answer_FileList 有几十 ms 顿挫）；② 应答帧 `emit signalRequestSend` 因收发两端 affinity 都是 GUI 线程，要绕一次 GUI 才能到套接字线程，界面卡住会拖慢控制应答。另发现 `ControlSession.cpp:252` `worker->isDone = true` 在 worker 线程裸写、GUI 线程持锁读，属数据竞争。
已按此改写文档"第三批遗留"段落。
